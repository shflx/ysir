# Karpathy 指南

用于减少 LLM 常见编码错误的行为规范

**注：** 这些规范更偏向谨慎而不是速度。对于非常简单的任务，应自行判断。

## 1. 编码前先思考

**不要假设。不要掩饰困惑。明确说出取舍。**

在实现之前：

- 明确写出你的假设。不确定时就提问。
- 如果存在多种理解，直接列出来，不要默默选一种。
- 如果有更简单的方案，应明确指出；必要时应提出异议。
- 如果某件事不清楚，就停下来。指出困惑点并提问。

## 2. 简单优先

**只写解决问题所需的最少代码。不要加入猜测性的内容。**

- 不添加需求之外的功能。
- 不为一次性代码做额外抽象。
- 不添加未被要求的“灵活性”或“可配置性”。
- 不为不可能发生的场景补错误处理。
- 如果你写了 200 行，而 50 行就够，就重写。

问自己一句：”资深工程师会觉得这过度复杂吗？“ 如果答案是会，就继续简化。

## 3. 外科手术式修改

**只改必须改的内容。只清理自己造成的问题。**

编辑现有代码时：

- 不要顺手“优化”相邻代码、注释或格式。
- 不要重构没有坏掉的东西。
- 尽量匹配现有风格，即使你本来会写成另一种方式。
- 如果发现无关的死代码，可以指出，但不要直接删除。

当你的修改制造出遗留项时：

- 删除那些因为你的修改而变得无用的 import、变量或函数。
- 不要删除既有死代码，除非用户明确要求。

检验标准：每一行改动都应能直接追溯到用户请求。

## 4. 目标驱动执行

**先定义成功标准，再循环执行直到验证通过。**

把任务转成可验证的目标：

- “增加校验” → “先为非法输入编写测试，再让测试通过”
- “修复 bug” → “先写出能复现问题的测试，再让测试通过”
- “重构 X” → “确保重构前后测试都通过”

对于多步骤任务，应先给出简要计划：

```text
1. [步骤] → 验证: [检查项]
2. [步骤] → 验证: [检查项]
3. [步骤] → 验证: [检查项]
```

强成功标准可以让你独立推进循环；弱成功标准（如“把它弄好”）则会不断需要额外澄清。
