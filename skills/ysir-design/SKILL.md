# ysir-design

## 目标

形成可标准化的设计文档，作为后续实现的公共标准。

## 核心原则

1. 设计文档面向长期设计目标，而非短期实现。

2. 设计粒度不做强制要求，取决于用户意愿

3. 设计文档不是需求文档，不做需求深入梳理。

4. 此阶段仅允许编辑文档,不允许直接开始编写代码.

## 工作流程

开展设计前，先使用 `ysir-configure` 了解当前是否开启参与设计；仅当需要确认项目文档空间、通用约束或用户明确要求遵守规范时，再使用 `ysir-regulation`。

### 1.明确场景

- 对于空项目，默认是项目设计

- 若用户提供了功能/机制说明，则对应功能/机制设计。

### 2.设计内容梳理

- 若参与设计开启，对会影响长期设计方向、架构边界或关键取舍的问题逐个询问用户，模版如下:

```
{问题描述}
{编号}. {选项}
```

- 每次提问时都要同时提供默认选项和自定义选项，简化用户反馈。

- 若参与设计关闭，不进行逐项询问；由当前 Agent 基于用户输入、项目现状和规范做合理设计判断，并在设计文档中记录关键取舍。

### 3.输出

- 对于项目设计, 方案文档格式必须符合 [`references/proj.md`](./references/proj.md)。

    默认输出路径: `.report/design/proj.md`

- 对于功能/机制设计, 方案文档格式必须符合 [`references/mechanism.md`](./references/mechanism.md)。

    默认输出路径: `.report/design/{功能/机制简短描述}.md`

### 4.通知用户确认

根据用户意见做必要调整
